## Update — 19 October 2026: double-check pass (still nothing committed)

Three independent reviews of the uncommitted work (admin auth/settings, payroll engine, mobile offline + migration) produced 50 findings. Every bug and risk is fixed and re-tested; the few nits that would have widened the scope are recorded in `HANDOVER.md` §8 instead.

### Security fixes (admin)
1. **2FA could be skipped.** The middleware decided "needs a code" from the factor list inside the browser cookie, which the browser can edit. It now uses the server-validated user and the signed session level.
2. **The cron secret was readable by every signed-in worker** (the settings table's read policy allowed all rows). Migration 0029 now narrows the policy *before* creating the secret, and the temporary row that was already in the live database has been removed. The route compares the secret in constant time.
3. **"Run now" bypassed the second factor and the deactivated-account check** because the whole route was exempt from the middleware. The exemption now applies only when the cron header is present; the browser call goes through the normal gates, and the route itself re-checks role, status and second factor.
4. Middleware failed open when a profile row could not be read; it now signs the user out.
5. The authenticator QR code was injected as raw HTML; it is now an image (Supabase returns a data URL).

### Payroll / reports fixes
6. **Filtered reports did not reconcile.** With an entity or project filter the unpaid break and the "primary company" were decided on the filtered rows, so a filtered total disagreed with the unfiltered report and with payroll. Rows are now grouped on the whole day first and filtered after; verified with a 4 h + 5 h two-project day and a 4 h + 4 h two-company day, and on the production build (Cotham Rd: same hours and cost with and without the filter).
7. **Push to Xero could silently send different hours than the run showed** (it recomputes from attendance). It now refuses with "The hours on this run no longer match the approved attendance … Click Recalculate" when they differ. Verified: 409, nothing sent, run status unchanged.
8. **The nightly auto-run re-created a run an admin had deleted.** It now handles each period once (`settings.auto_pay_run.lastPeriodEnd`); "Run now" still always attempts.
9. Also fixed: the labour-cost alert could not be switched off; unpaid-break minutes were reset to 30/5 when the rule was turned off; monthly pay cycles drifted for anchors on the 29th–31st; auto-run body validation (400 on a bad period or entity id); reminder de-duplication by title instead of a wildcard match; one budget check per run instead of per entity; the dashboard tile shows paid hours (and the breaks); CSV cells starting with `= + - @` are neutralised for Excel; the preview's row count is per entity; admin-only checks on the Xero preview/push routes; the Pay-settings text says only the primary company's break rule applies.
10. Migration 0029 now also writes the unpaid-break default into each entity's `pay_config`, adds a `site_url` setting (no hard-coded domain in the cron function), sets a 30 s timeout on the cron call, removes any non-VIC holiday rows, and toggles the settings audit trigger around the secret insert.
10a. **PAY-04 "Apply pay rates effective on the worked date" was not actually built** (found while answering "which Original tasks are unfinished"): every rate lookup took the employee's *latest* rate, so a pay rise entered mid-period would have repriced the whole period. Now each worked day is priced with the rate in force that day (payroll entries, reports, dashboard, budget alerts); the Employees edit form has a "New rate applies from" date (default today); correcting a rate for the same date replaces it instead of adding a twin row. Verified with engine checks (two 8 h days across a $40 → $50 rise = $675; back-dated day; same-date twins; no-rate employee still reported) and live on the production build (temporary rise for one Build One employee from 18 Sep: run gross equals an independent per-day pricing, and differs from "latest rate for every day").
10b. **Migration `0030_pay_rate_baselines.sql` (new, needs applying):** every existing rate row is dated the day it was *typed in* (late Sep / early Oct), not the day the rate started, while attendance goes back to 2 Sep. The first live check showed the trap: a rise back-dated before that typed-in date looked *older* than the original rate. 0030 dates each employee's first rate 2000-01-01 (their baseline) and removes exact twin rows; new employees' first rate is written the same way. **One thing for the client to confirm before recalculating the 25 Sep – 8 Oct runs:** Dylan Bell has $44 from 28 Sep and $42 from 6 Oct (each entered twice). Under per-day pricing his days up to 5 Oct are paid at $44 and from 6 Oct at $42; the existing runs used $42 for everything. If the $44 was a typo, edit Dylan in Employees: rate 42, "applies from" 01/01/2000 (that replaces the baseline row). Lachlan Eames has the same pattern for 3 cents ($23.45 → $23.48 from 6 Oct).

### Mobile offline fixes (7.6, new preview build)
11. **Offline clock-in could not work on a cold start** (no project list). The entity and project lists are now cached on the phone and used when there is no signal, with a note on screen.
12. **A session clocked in online was invisible after a restart with no signal**, so Home offered Clock In again (double clock-in, 16 h paid). The last open server session is cached; the clock-in screen refuses with "Already clocked in".
13. **A clock-out tapped during a sync could be lost** (the sync overwrote the queue with a stale copy). Every queue change now goes through one lock and removes items by id; a local-id → server-id map is kept.
14. **Any non-network error dropped the item silently.** Only definite rejections (bad data, constraints) give up, and those appear on Home as a red "could not be sent" card for the worker to report; temporary errors (outage, expired token, captive portal) are retried up to 20 times.
15. **A queued clock-out was ignored when the server still showed the session open**, which could trigger a bogus auto clock-out; Home now respects the queue.
16. Also: the "worker's real time wins" reconcile only overrides the automatic 16 h cap and compares instants (not strings); overtime is carried on that path; selfies are copied into the app's documents folder so the OS cannot purge them (`expo-file-system` added, already part of the SDK); the queue is keyed by user; overlapping Home refreshes are coalesced; an expired login with no signal still saves the clock-in on the phone; copy fixes ("It/They", "recorded"). The reachability probe used before a sync allows 5 s (the first HTTPS handshake after signal returns is slow on site); a shorter 2.5 s probe produced a spurious "Still offline" on the emulator the moment the link came back, caught by the device test.
